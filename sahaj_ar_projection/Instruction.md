## 3. Primary hypothesis (to test, not to assume)

Wrong or stale `landmark_id` values lock in and are never corrected.

Code facts verified by reading the source on 19 Oct 2026 (line numbers may drift; search by name):

1. `ar_projection/pipeline.py`, in `Pipeline.process`, the loop that removes map IDs whose reprojection disagrees with the pose by more than `ransac_reprojection_threshold_px` runs **only inside `if pose.valid:`**. In landmark-only mode most frames are invalid, so the cleanup rarely runs.
2. `ar_projection/landmarks.py`, `associate()`, keeps any inherited `landmark_id` that exists in the map and is not already used. It does no geometric check. It only runs descriptor matching for features whose `landmark_id` is `None`.
3. `ar_projection/features.py`: LK flow copies `landmark_id` forward (`association_source="lk"`). ORB redetection can carry an old `landmark_id` to a new detection when descriptor and 5 px spatial checks pass (`association_source="orb_redetection"`).
4. Net effect: a bad ID, once assigned, rides LK indefinitely during LOST. Because it already has an ID, fresh descriptor matching never replaces it.
5. The map stores one descriptor per landmark (from its first accepted view), so fresh descriptor matches from other views are also weak. This is a second, separate hypothesis (Step 4).

Competing hypotheses are listed in `CONTEXT.md` section 17: appearance/view coverage, bad map geometry, scene or camera change, RANSAC limitation. Step 2 data should discriminate between them before Step 3 changes behavior.

- Decision / next step: do not enable `mapping.multiview_descriptor_bank` in any shipped config as implemented (original cut). The correct fix is to aggregate each landmark's multiple descriptors to a single best-distance-to-this-landmark figure *before* running the ratio test across landmarks (not raw rows) — implemented next, see the follow-up entry below. Step 3 (ID lifecycle) remains untried and is unaffected by this result.
